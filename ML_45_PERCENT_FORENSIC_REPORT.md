## 5. Why 45.1% Appears

The value `45.1%` appears because the model outputs `0.45134398341178894` directly from the sum of the leaf weights of the XGBoost trees passed through a sigmoid function. The frontend merely multiplies by 100 and rounds to 1 decimal place using JavaScript's `.toFixed(1)`. There is no artificial manipulation.

## 6. Why Multiple Candidates Have Same Probability

The primary issue is a **lack of variance in candidate-specific features**. 

During candidate generation, 50 ATMs are selected. The feature builder (`ml/features/feature_builder.py`) extracts 28 features. However, 24 of these features (transaction, temporal, behavioral, graph) are **case-level features** extracted for the suspect's account, not the individual ATM.
Because all 50 ATM candidates belong to the same case (`C-2026-9081`), they have **exactly identical values for 24 out of 28 features** (standard deviation = 0.0).

The only differentiating features are 4 spatial features (e.g., `atm_proximity_score`, `distance_to_case_center`). The XGBoost trees evaluate splits based on these features, but because the thresholds in the trees are relatively coarse (e.g., `distance_to_case_center < 1.28`), all top candidates for this case fall on the exact same side of the tree splits. Consequently, all top candidates end up in the **exact same terminal leaf nodes** across all 32 trees, yielding identical final probabilities.

## 7. Ranking Logic

If all candidates have the exact same probability (0.45134398), why do they have different ranks?
The ranking logic (`ml/prediction/ranking.py`) explicitly separates the ML probability from the final order using tie-breakers:
```python
sort_cols = ['probability', 'atm_proximity_score', 'atm_id']
sort_asc = [False, False, True]
```
Even when probabilities tie, `atm_proximity_score` breaks the tie. For `C-2026-9081`, ATM-0184 has a higher proximity score (10.0) than ATM-0099 (4.69), so it gets Rank 1.

## 10. Data Quality Findings

Training occurs in `ml/training/train.py`.
- **Training rows:** Only 50 cases are sampled.
- **Candidates per case:** 50
- **Total training rows:** ~2500
- **Target Construction:** For each case, the single true fraud ATM gets `y=1`, and the other 49 ATMs get `y=0`.
- **Class Imbalance:** Base rate is ~2%.
- **Variance Issue:** Because training data consists of 50 positive examples and 2450 negative examples where 49 negatives share identical case-level features with the 1 positive example, the model struggles to differentiate candidates using anything other than the 4 spatial features.

## 13. Root Cause

- **CONFIRMED**: The 45.1% value is real ML output, formatted to one decimal place by the frontend.
- **CONFIRMED**: Multiple candidates receive identical probabilities because they share identical case-level features (24 out of 28 features).
- **CONFIRMED**: The spatial feature thresholds in the XGBoost trees are too coarse to distinguish the top candidates for this case, placing them in identical leaf nodes.
- **CONFIRMED**: The differing ranks are strictly the result of a deterministic sorting tie-breaker (`atm_proximity_score`), independent of the identical ML probabilities.

## 14. Recommended Fixes for ML Teammate

- **Enrich Candidate-Specific Features**: The model needs more features that vary per ATM candidate (e.g., historical fraud rates at the specific ATM, distance from suspect's historical transaction cluster, ATM hardware type).
- **Fix Data Leakage in Train/Test Split**: Use `GroupShuffleSplit` on `case_id` during training instead of random `train_test_split` to ensure rows from the same case don't leak across train/test boundaries.
- **Tune Hyperparameters**: Max depth 4 may be too shallow to fully utilize the spatial features, or `min_child_weight` might be preventing finer splits.
- **Address Class Imbalance**: With a 1:49 ratio, use `scale_pos_weight` or undersampling so the model isn't biased toward predicting low probabilities for all candidates.
